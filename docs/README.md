# Financial Data Agents Documentation

The documentation is divided by **what you are trying to do**, not by how technical you happen to be.

## Using Financial Data Agents

Installation, configuration, everyday usage, analysis strategies, financial formulas, terminology, and optional local-AI hardware guidance:

**→ [Investor & User Documentation](user/README.md)**

A software engineer installing the application is still a *user* for this purpose.

## Reviewing or developing the project

Architecture, design rationale, roadmap, milestone plans, active step/slice status, engineering contracts, [quality gates](project/README.md#quality-gates), and deployment artifacts:

**→ [Project & Technical Documentation](project/README.md)**

An investor who is curious about the project's architecture is welcome there too, but ordinary use of Financial Data Agents should not require reading project-planning material.

## Maintaining shared guidance

Describe shared installation, storage, provider, presentation, and architecture
behavior in terms of capabilities and contracts. These guides should not need
revision merely because another analysis strategy is added. Keep strategy
discovery in the [Analysis Strategy Guides](user/strategies/README.md) and CLI
help rather than repeating an exhaustive inventory across general guides.

Name a strategy when documenting its formulas, supported options, provider
requirements, applicability rules, or a concrete example. Label examples as
examples; do not imply that every strategy supports the same inputs or options.
Historical plans, review records, and test evidence retain the specific names
needed to describe their scope accurately.
