# PH.3 — Provider check and health JSON: slice plan

Owned by [PH](PH_CONTRACT_AND_SLICE_PLAN.md#ph3a--health-json-and-the-not-configured-outcome). The decisions are in
the [PH.3 decisions](PH3_CANARY_AND_HEALTH_JSON_DETAIL.md) and are not repeated here: this plan holds the files,
tests and output changes of PH.3a, PH.3b and PH.3c as built.

## 1. At a glance

- **PH.3a (built):** `ian health --json` writes one typed document; a check that cannot run because SEC access
  is not set up is `not_configured`, apart from `failed`, which now means only an unexpected error inside a check.
- **PH.3b (built):** after a provider failure, one bounded probe of the implicated provider puts a verdict on
  a first line in the text modes, with the `--no-provider-check` option and the `PROVIDER_CHECK` settings. In
  `--json` mode it prints nothing extra, so JSON carried no verdict until PH.3c.
- **PH.3c (built):** the `provider_check` element in the failure envelope, the four strategy documents and the
  refresh summary, and the check now runs in `--json` mode.
- **What neither does:** change a check's requests, probe ticker or timeout; change an exit code; retry, repair or
  switch provider.
- **Rules:** stored data has no compatibility value; no new dependency; no real service in a test.

### Tests

- Each of the six outcomes, in text and in JSON, with the exit code (0 for `ok`, 1 for the other five).
- The JSON validates against `ProviderHealthDocument`; the checked-in schema lists the six verdicts in the order
  of `CheckVerdict`; the model's verdict values equal `CheckVerdict`'s.

- `not_configured` follows from the typed field and not from the detail wording; an adapter failure that carries
  no kind is `failed`, not `not_configured`.
- The schema drift check and the JSON-command conformance test pass with `health` listed.

### What was built

- The probe, `ProviderProbe` in [`src/data/provider_probe.py`](../../../../../investment_analysis_engine/data/provider_probe.py), runs the shared
  check body of one provider in a daemon thread under the time limit (passed through the body's spec, not by changing
  the body), waits at most the limit plus a short documented grace period, and maps the health outcome to a verdict
  (P6). A raised exception, a hang or a value that is not a check result gives `not_checked`; the probe never raises.
  Each entry of `PROVIDER_CHECKS` now accepts an optional time limit and names its library.
- **Grace beyond the time limit.** The check body enforces its own whole-check deadline, so the probe normally returns
  at the limit. The probe also waits an extra 2 seconds (`_BODY_GRACE_SECONDS`) for the body to return before it stops
  waiting and reports `not_checked`, so a body that fails to honour its limit still cannot hold a command. The
  worst-case wait is therefore 12 seconds per provider at the default limit of 10 seconds (the limit plus 2 seconds), and
  at most 24 seconds for a command that implicates both providers, since they are checked one after the other.
- Each strategy's execution module exposes `capture_provider_failure`, which the normalizing function, the two
  Graham commands and `fcf-growth` use; `ExecutionCapture` and `RefreshJobResult` carry the `provider_failure`
  element in memory only, for all three job outcomes: a saved run (from the capture), an unsaved outcome (from the
  capture) and a raised job (from the exception). Nothing new is stored and the refresh document is unchanged.
- `refresh` runs the check once after the batch, for the providers the jobs' elements implicate.

### What was built

- `ProviderCheckFindings` (in `src/cli_provider_check.py`) holds the probe's findings in the order of the
  implicated providers' most severe failed kind. `provider_check_findings(failures, choice)` is the one function that
  asks the probe; `with_provider_check` and `echo_provider_check` write its lines, and `element()` is its document form.
- **Raised failures.** `execution_errors` builds the failure envelope, asks for the findings from the envelope's
  `provider_failure`, and writes either the lines (text) or the envelope carrying the element
  (`FailureEnvelope.with_provider_check`, which validates it against `provider_failure`).
- **Returned failures.** `graham-number`, `graham-growth` and `fcf-growth` take the findings from the captured
  `provider_failure`, pass the element into the presentation (or the FCF renderer), and prefix the lines in text modes.
- **Refresh.** After the batch, one set of findings comes from the jobs' in-memory `provider_failure` elements; text
  mode prints the lines before the summary and `--json` writes the element as the summary's last key.
- The refresh help text no longer says the finding is printed in text output only.
