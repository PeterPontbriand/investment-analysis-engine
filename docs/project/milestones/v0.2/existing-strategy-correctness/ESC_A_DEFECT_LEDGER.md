### ESC-21 — Frozen-clock skew tolerance and the consolidated availability check have no IR record

**Scope/severity:** every analysis that resolves provider facts or quotes through the shared resolver (Graham Number, Graham Growth, FCF/Earnings Growth) and the freshness checks they use; low-to-medium public-behavior and record gap, not a wrong output. Found by ESC-E.1's change inventory, not by a stakeholder report. **Source revision:** commit `5f01ac0` ("tolerate expected clock skew in timestamp-vs-boundary checks"), part of IR.2.4 on PR #48, squash-merged as `af7bad1`.

**What changed, accurately.** `5f01ac0` did not remove the future-availability check. It replaced three hand-written `available_at > now` comparisons (two in the shared input resolver's provider-response and cache-hit paths, one in its fact validation) with the shared `evaluate_freshness` check in `src/data/quality.py`, which is now the single owner of the decision. That check tolerates up to `FROZEN_CLOCK_SKEW_TOLERANCE` (ten minutes, defined in `src/core/clock.py`) between the frozen `executed_at` and a provider timestamp on a live run, and tolerates nothing on an `--as-of` run, where a timestamp after the boundary is look-ahead. `src/data/financial/quote_freshness.py` clamps a quote's retrieval age and tolerates the same amount for the observation timestamp. The commit message gives the reason: since IR.2.3 the resolver's clock is frozen at the run's start, so a live quote stamped when the fetch completes looked like a future timestamp, and live Graham quote resolution failed with "future_timestamp".

**Why it is a ledger entry.** No IR plan or acceptance record names the tolerance, its size, or the consolidation. The only sources are `docs/project/ARCHITECTURE.md` (the Frozen-clock skew passage) and the commit message, the same kind of source as ESC-20. E.1 also found no difference attributable to it, because no pair produced a timestamp near the boundary.

**Expected contract.** A live run accepts a provider fact or quote stamped within ten minutes after `executed_at`, from the provider and from a cache hit, and rejects one stamped beyond that. An `--as-of` run rejects a fact available even one second after the boundary.

**Disposition (approved by the project owner, 2026-09-30):** no code change. Record the tolerance and the consolidation in the IR.2 acceptance record's list of changes (done, commit `e48a122`). Verification is by offline tests, in E.2 for the Graham resolver path and in E.4 for Momentum's historical path.

**Verification, Graham resolver path (E.2, 2026-09-30):** `tests/analysis/graham_value/test_clock_skew_tolerance.py` (24 offline scenarios, each run against both Graham resolvers) confirms the expected contract for provider facts, cache hits and quotes on a live run, and the zero-tolerance rule on an `--as-of` run. The existing tests in `tests/data/test_quality.py` and `tests/data/test_quote_freshness.py` cover the shared checks directly but not the resolver or a cache hit. **Verification, Momentum (E.4, 2026-09-30):** Momentum's historical path does not use the shared freshness check, so the tolerance does not apply to it. Its boundary checks are a strict truncation to bars at or before `as_of` and a data-quality check on the fetched frame. `tests/analysis/momentum/test_momentum_boundary.py` tests the truncation: a bar exactly at the boundary is kept and one a second later dropped. The review also produced ESC-22 and ESC-23. ESC-21 is verified for both paths.

**Closed (2026-10-01):** the tolerance and consolidation are recorded in the IR.2 acceptance record (`e48a122`) and verified offline for the Graham resolver (E.2) and Momentum (E.4); ESC-23's repair (`d9fa796`) makes Momentum's live path follow the same tolerance.

### ESC-22 — A Momentum `--as-of` run fails when a bar after the boundary is invalid

**Scope/severity:** Momentum with `--as-of`, every mode; low availability and documentation finding, not a wrong value. Found live during ESC-E.2's cross-cutting run and confirmed offline in E.4. **Source revision:** IR.2.3 (PR #48, `af7bad1`), which made the resolver check and publish data quality once against the raw provider fetch and the analyzer re-check the truncated frame.

**Reproduction:** on 2026-10-01 at 00:30Z Yahoo returned non-finite prices for the 2026-09-30 row. `ian momentum KO --as-of 2025-12-31` failed with the sanitized `historical_quality` rejection naming 2026-09-30, although every bar up to the boundary was valid and the bad bar can never reach the calculation. Offline: `tests/analysis/momentum/test_momentum_boundary.py::test_as_of_run_fails_closed_when_a_bar_after_the_boundary_is_invalid`.

**Expected contract:** the ESC plan's Time dimension requires that information after the boundary cannot silently enter a historical result. It does not enter; the run fails closed, which is the safe direction. Nothing documents that a historical request depends on the integrity of later data, and `MOMENTUM.md` does not say so.

**Disposition (proposed):** no code change; add one sentence to `docs/user/strategies/MOMENTUM.md` saying an `--as-of` run is rejected if any fetched bar, including one after the boundary, is invalid. A code change (check quality on the truncated frame only) would turn some failures into results, so it needs the project owner's decision.

**Decision and closure (project owner, 2026-10-01; closed):** repaired in commit `d55c450`, with no new parameter. `MomentumInputResolver.resolve` passes `end_date` to `fetch_historical_data` when `as_of` is set: the day after the boundary's UTC date, because providers treat the end date as exclusive and bars are dated, so every bar on the boundary's date is fetched. The strict truncation to bars at or before `as_of` stays. Live runs pass no `end_date` and are unchanged. `CachedHistoricalDataClient` and the provider interface needed no change: `end_date` was already forwarded and already part of the cache key, so an `--as-of` run is cached separately from a live run. The Yahoo client passes it to `yf.download(end=...)`; the placeholder Massive client built its range with it inclusively, so the project owner had `end_date` defined as exclusive in the `BaseDataClient` and `MarketDataProvider` docstrings and the Massive client changed to match (`2987446`, tested in `tests/data/test_massive_client.py`); the evaluation fixture provider ignores it and the truncation still applies. A boundary earlier than the configured `start_date` is reported as `no_eligible_observations` (the ESC-24 text) by a guard in the resolver before anything is fetched (commit `40a9363`; tests first: `--as-of 1990-01-01` and a boundary one second before the start date never call the provider and write no cache entry, and a boundary at the start date is fetched and keeps the first bar). A first version fetched such a window as a live run does, to avoid editing an accepted conformance test; the project owner authorized the one-line `start_date` change in `tests/analysis/test_base_analyzer_conformance.py` (its boundary preceded its own start date) and the guard replaced that workaround.

**Tests first** (`tests/analysis/momentum/test_momentum_as_of_fetch.py`, through the production `CachedHistoricalDataClient` and a SQLite repository, with a fake provider that honours `end_date` with Yahoo's exclusive semantics): an invalid bar after the boundary no longer fails an `--as-of` run on a cache miss, a cache hit or with `--no-cache`; an invalid bar at, before or well before the boundary still fails, with and without the cache; the cache entry for an `--as-of` run holds no bar after the boundary and no live-keyed entry is written; a live run still fetches and caches the full history under its own key; the requested end date for several boundaries, a month end and a non-UTC offset. The earlier test that pinned the old fail-closed behaviour was removed. Gate: 3,451 tests, 91%. Live check on 2026-10-01 against Yahoo: `ian momentum KO --as-of 2025-12-31` fetched and cached 1,255 bars (request end 2026-01-01, last bar 2025-12-31) and a live run cached 1,442 bars under a separate key; the `--as-of` values equal the earlier output within the usual provider noise.

**The one remaining case:** a bar dated on the boundary's own date but stamped after the boundary instant is fetched (it falls inside the requested window) and truncated, and if it is invalid it still fails the run. Yahoo's daily bars are stamped at midnight, which is never after a boundary on the same date, so the case cannot occur with them; it applies only to a provider that stamps a daily bar later in its date. It is tested (`test_an_invalid_bar_dated_on_the_boundary_day_but_stamped_after_the_boundary_instant_still_fails`) and noted in `MOMENTUM.md`.


### ESC-23 — A live Momentum run does not check bar dates against the execution time

**Scope/severity:** Momentum without `--as-of`; low Time finding; no known real-world trigger. Found by E.4's boundary review. **Source revision:** predates the baseline; unchanged by IR.

**Reproduction:** `MomentumAnalyzer.run_analysis` with `as_of=None` and a frame whose last bar is dated 2099-01-01, `executed_at` 2026-01-20: the run succeeds, reports that bar as the latest close and `data_as_of` 2099-01-01. The resolver truncates only when `as_of` is given, and its quality check has no timestamp-versus-boundary rule (the shared freshness check with the ten-minute tolerance, ESC-21, is not used on this path).

**Expected contract:** a live run's boundary is `executed_at`. A bar dated after it, beyond any exchange-time skew, is not knowable information.

**Disposition (proposed):** record it as a known limit in the final acceptance record; no code change now. Rejecting bars dated after `executed_at` plus the skew tolerance is a possible later repair, but it would turn a result into a failure for such data, so it needs the project owner's decision. Real providers date bars at or before the current instant, so no live trigger is known.

**Decision and closure (project owner, 2026-10-01; closed):** repaired in commit `d9fa796`. A live run fails the quality check (rule `historical.future_observation`, reason "An observation dated ... is later than the execution time beyond the allowed clock skew.") when a bar is dated more than `FROZEN_CLOCK_SKEW_TOLERANCE` after `executed_at`; the bar is not dropped. `--as-of` runs are unaffected because truncation excludes later bars. Tests first: `tests/analysis/momentum/test_momentum_boundary.py` (within the tolerance accepted; just beyond, an hour and thirty days rejected; an `--as-of` run unaffected). Gate: 3432 tests, 91%.

### ESC-24 — Momentum `--as-of` before the first observation reports a generic error, not the cause

**Scope/severity:** Momentum with `--as-of`, every mode; low-to-medium presentation and public-contract defect. Found in E.4's Inputs review. **Source revision:** IR.2.6 (PR #48), which added `--as-of` to Momentum.

**Reproduction:** `ian momentum KO --as-of 1990-01-01` on `main`, 2026-10-01. Exit 1. Text: "Unable to complete momentum analysis for KO: the returned price history could not be analyzed." JSON: `"status": "error"`, `"reason_code": "invalid_input"`, empty `diagnostics`. The price history is valid; the boundary simply precedes it. The resolver raises `ValueError("No historical observations are eligible at the requested as_of boundary.")`, and the CLI's generic handler discards that message. Graham and FCF report an unavailable boundary as `input_unavailable` with a specific reason.

**Expected contract:** ESC-11 requires failures to be typed and sanitized with an actionable cause, and the Inputs dimension requires insufficient or unavailable history to be distinguished from invalid input.

**Disposition (proposed, needs the project owner's decision):** report this case as `input_unavailable` with the reason "No price history is available at or before the requested `--as-of` boundary." in text and JSON. That changes a public JSON `status` and `reason_code` for this case, and Momentum's failure wording, so it is not applied here. A wording-only alternative keeps `status` and `reason_code` and replaces only the reason text.

**Decision and closure (project owner, 2026-10-01; closed):** repaired in commit `dfd0cf6` as proposed. The resolver raises `NoEligibleObservationsError`; text and JSON report `status: input_unavailable`, `reason_code: no_eligible_observations` and the reason "No price history is available at or before the requested --as-of boundary.". The reason code is new to Momentum's JSON, so Momentum's presentation `schema_version` is now 5 (`USAGE.md` updated, as ESC-20's disposition requires). No calculated value changed. Tests first: `tests/test_existing_strategy_failure_output.py`, `tests/analysis/momentum/test_momentum_boundary.py`. Gate: 3425 tests, 91%. A boundary earlier than the configured series start date takes the same path without fetching anything (`40a9363`, ESC-22).

### ESC-25 — A historical frame with a non-datetime index passes quality as insufficient evidence and yields 1970 provenance

**Scope/severity:** every strategy that consumes a historical price frame through the shared quality check (Momentum today); low-to-medium Time and provenance finding; no known real-world trigger. Found while removing a test-fixture artifact in PR #83; tracked as issue #84. **Source revision:** Step 3.3 (PR #32), which introduced `_index_result`.

**Reproduction:** `tests/analysis/momentum/test_momentum_integer_index.py`, on `main` at `07a818a`, 2026-10-06. `MomentumAnalyzer.run_analysis` with a five-row frame on a default integer index succeeds. Every `ResolvedInput.observed_at` is `1970-01-01T00:00:00Z` and `MarketDataContext.data_as_of` is 1970-01-01, because `pd.to_datetime(frame.index, utc=True)` (`src/strategies/momentum/analyzer.py:364`) reads the integers as epoch nanoseconds; the only signal is pandas' `Discarding nonzero nanoseconds` warning. `evaluate_historical_quality` reports `historical.index` as `INSUFFICIENT_EVIDENCE` and no rule as `FAIL`. The cause is `_index_result` (`src/data/quality.py:182-184`), with the same treatment in `_context_result` (line 194), `_sessions_result` (line 214) and `evaluate_future_observation` (line 235); the analyzer stops only on `FAIL` (`analyzer.py:340`, `351`). Providers cannot trigger it today: yfinance returns a `DatetimeIndex` and the Massive client's mock builds one.

**Expected contract:** the Time dimension requires that unavailable information cannot silently enter results, and provenance must not state a date the provider never supplied. The Step 3.3 plan records the current treatment as deliberate: "unsupported non-date indexes report insufficient evidence, preserving representation-bypass compatibility" (`docs/project/milestones/v0.2/step-3.3/STEP_3_3_CONTRACT_AND_SLICE_PLAN.md:96`). It gives no example of a caller that relies on that compatibility, and the plan does not explain why a frame that cannot be dated is acceptable to calculate from.

**Disposition (proposed, needs the project owner's decision):** the shared check returns `FAIL` for a non-datetime index, so no strategy proceeds on it. That turns a result into a failure for such frames, reverses the Step 3.3 decision above, and changes `src/data/quality.py` and its tests, so it is not applied here. One scope question needs deciding with it: the SQLite market-data cache supports a `date` index kind (Python `date` values; `src/data/repositories/market_data.py:152-154`, `206-208`), and `pd.to_datetime` converts such an index correctly. A blanket `FAIL` for every non-`DatetimeIndex` would reject that supported shape; the alternative is to fail only an index that is not date-like. The decision also covers whether the failure carries a sanitized reason code of its own or reuses `historical_quality`, which would change a public reason code if new. Tests first: `tests/data/test_quality.py` (integer index fails; date-like index per the decision) and `tests/analysis/momentum/test_momentum_integer_index.py`, which would assert the rejection instead of the acceptance it pins now.
